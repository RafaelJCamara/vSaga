# Review: security

Security review of the auth-backend, auth-frontend and packaging blueprints, plus the data-access parts of the others: 1 blocker, 7 major, 8 minor. This was a read-only pass. Nothing was built or run, so nginx behaviour and the address nginx sees on Docker Desktop come from documentation and need confirming in live verification.

What holds up and needs no rework:
- The cookie and antiforgery design. Tokens are bound to the sub claim and reissued after HttpContext.User is replaced. Angular's XSRF interceptor only fires same-origin (checked in node_modules/@angular/common/fesm2022/_module-chunk.mjs:1371-1397).
- SameSite=Strict plus an Origin check on the hub, and X-Forwarded-For with ForwardLimit 1.
- 403 before any read for an out-of-scope route type, and filtering of correlations, children and saga-types.
- The last-administrator check inside an exclusive scope (Microsoft.Data.Sqlite 10.0.11 contains BEGIN IMMEDIATE).
- The SPA has no innerHTML or sanitizer bypass, and index.html loads nothing external.

What has to change before the plan is final:
- Blocker: a retry is a republish by message type, so a scoped sagas.retry reaches other saga types. The sample reproduces it.
- Major: the setup path lets the first network visitor become Administrator, and a rejected seed password reopens it.
- Major: packaging and auth-backend define CORS, forwarded-header trust, the identity path and cookie naming twice, with different values.
- Major: the demo publishes an Administrator login on every interface.
- Major: lockout and the per-address limiter can be used to deny sign-in.
- Major: the SPA and the API disagree on admin payload names, so "disable user" would be silently ignored.
- Major: hub connections survive a password change and sign-out.
- Major: errorMessage is not redacted for callers without sagas.data.

## 1. [blocker] (auth-backend (the fix touches the engine file that engine-snapshots also edits))
A retry is not confined to the saga type the caller is authorised for. The blueprint checks sagas.retry against the saga type in the route. But the redrive is a republish by message type, under the same correlation id, with a fresh message id, and every saga type subscribed to that message type processes it as a new delivery. A user whose sagas.retry grant names one type can therefore re-run steps, with their business side effects, in types they hold no grant for. The sample reproduces it: retrying a TimedOut InvoiceFollowUpSaga replays InvoiceIssued, and PostShipmentChoreography handles it again and starts a second InvoiceDeliverySaga (a second customer email).

**Evidence:** C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Endpoints/SagaEndpoints.cs:192-205 (comment 'every saga type subscribed to this message type sees it', then PublishRawAsync with MessageEnvelope.New(correlationId)). C:/Users/rafae/Documents/Projects/vSaga/docs/dashboard.md:42-47. C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Core/Runtime/SagaOrchestrator.cs:399-431 and 469-487 (any type with an instance for the id, or able to initiate, runs the step when the message id is new). C:/Users/rafae/Documents/Projects/vSaga/dotnet/samples/VSaga.Samples.OrderProcessing/InvoiceFollowUpSaga.cs:82-87 and C:/Users/rafae/Documents/Projects/vSaga/dotnet/samples/VSaga.Samples.OrderProcessing/PostShipmentChoreography.cs:122-128 (both handle InvoiceIssued under one correlation id). C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Core/Dsl/ChoreographedSagaDefinition.cs:105-130 (the step runs whatever the instance's status). Blueprint auth-backend section 8, retry row.

**Fix:** Make the redrive targeted. Add a header constant to MessageEnvelope (for example TargetSagaTypeHeader = 'x-vsaga-target-saga-type'). The retry endpoint publishes with it set to the route's saga type. SagaOrchestrator.HandleCoreAsync returns before deserialising when the header is present and differs from SagaType, so the message is acknowledged and nothing is logged. Tests: a Core test where a second saga type ignores a targeted message, and an API test that the republished envelope carries the header. An engine host older than this change ignores the header, so state the minimum engine version for scoped retry in ADR 0006 and in docs/dashboard.md under Manual retry. If the engine change is declined, either refuse a scoped caller's retry with 403 when FindByCorrelationIdAsync returns a saga type outside the caller's sagas.retry scope, or honour sagas.retry only from an unscoped grant, as access.manage already is. Consumers that are not sagas still receive the replay; say so in the user guide.

## 2. [major] (auth-backend, auth-frontend)
The first-administrator path can hand the dashboard to whoever reaches the port first, and a seeding mistake reopens it. POST /api/auth/setup is anonymous and asks for nothing only the operator has. It works for Dashboard:Setup:WindowMinutes after every process start while the store has no users, and GET /api/auth/session advertises that state. An empty store also occurs after a lost or wrongly mounted volume. Separately, the blueprint says an invalid seed password 'logs an error and leaves setup available'. An operator who set Dashboard:Admin:* expects no setup screen, yet gets an open claim window on every restart.

**Evidence:** Blueprint auth-backend section 10 ('An invalid seed password logs an error and leaves setup available'; 'POST /setup re-checks both inside an exclusive scope'), section 7 (setup is anonymous; the session response returns setupAvailable), section 6 (default path under LocalApplicationData, which is the container layer when no volume is mounted). C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Dockerfile:21-29 (no volume and no user today). The race between two first visitors is itself handled by the exclusive scope.

**Fix:** 1) Require a one-time setup code. Generate it at start when no users exist, log it once at Warning in the API log, require it in the setup request (fixed-time comparison, inside the auth rate limiter), and add the field to the SPA setup page. Allow Dashboard:Setup:Code to preset it. 2) Fail closed on seeding. When either Dashboard:Admin key is set, setup is never available. A seed that cannot be applied leaves setupRequired true and setupAvailable false, marks the identity health check Degraded with the reason, and returns a problem code the SPA can show. 3) In a container (DOTNET_RUNNING_IN_CONTAINER=true) refuse the implicit default path: require Dashboard:Identity:Sqlite:Path and log the resolved path at start. 4) Tests: setup without the code is rejected; setup with seed keys present is 409; a weak seed password does not open setup.

## 3. [major] (packaging, auth-backend)
Packaging and auth-backend each define the same four security settings, with different values. (a) CORS: packaging makes Dashboard:WebOrigin optional with CORS off. Auth-backend keeps the default http://localhost:4200, calls UseCors unconditionally and lets the hub origin guard accept that origin. Cookies ignore ports, so under the auth-backend version whatever is served on localhost:4200 (another stack's UI, or any other dev server) can read an overlay API with the user's session, read XSRF-TOKEN from document.cookie, send it in the allowed header and open the hub. (b) Forwarded headers: packaging trusts an explicit list with ForwardLimit 1. Auth-backend adds its own registration where '*' trusts every peer, and says compose leaves the key unset. (c) Identity path, volume and Dockerfile runtime lines: /var/lib/vsaga-dashboard versus /data. If the mount and the configured path disagree, the database lives in the container layer, and users, roles and the key ring vanish on recreate. (d) Per-stack cookie names: a port suffix computed per request versus Dashboard:Session:CookieName.

**Evidence:** C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Program.cs:31-34 and C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/appsettings.json:15-18 (today's fallback origin with AllowCredentials and AllowAnyHeader). Blueprint auth-backend section 11 (WebOrigin default http://localhost:4200, TrustedProxies empty), section 5 services step 9 ('* clears both lists'), pipeline steps 2-3, section 12 (/data). Blueprint packaging sections 3, 5 and 6 and its cross-assignment contracts.

**Fix:** Give packaging's DashboardEdge sole ownership of CORS and forwarded headers, and delete auth-backend's step 9 including '*'. Default Dashboard:WebOrigin to empty; the hub guard accepts it only when it is set. A cross-origin SPA cannot send the XSRF header (Angular adds it same-origin only), so document WebOrigin as read-only cross-origin access or drop it. Pick one identity path (packaging's /var/lib/vsaga-dashboard) and one owner for the Dockerfile runtime lines, and assert in the compose CI job that Dashboard__Identity__Sqlite__Path sits under the mounted volume. For cookie names use the configuration key: the framework's antiforgery cookie name is fixed at start, so a per-request port suffix cannot work. Accept that XSRF-TOKEN stays shared between stacks and document one signed-in stack per host name, with http://127.0.0.1:<port> for a second.

## 4. [major] (packaging (uses auth-backend's seeding))
After this change the demo publishes a working Administrator login and a data-reading API key on every network interface. The compose ports bind 0.0.0.0, the seeded administrator uses the committed password with no forced change, and the README prints both. Anyone on the same network can sign in, retry sagas and manage users, and the key (Viewer) reads every payload and state blob. A peer that reaches port 5080 directly also sits inside the trusted proxy ranges and can forge X-Forwarded-For.

**Evidence:** C:/Users/rafae/Documents/Projects/vSaga/docker-compose.yml:33-34 ('5080:8080') and :40 (committed key). Blueprint packaging section 3 ('4200:8080', Dashboard__Admin__Password, Dashboard__TrustedProxies listing all private ranges) and its open question. Blueprint auth-backend section 10 (the seeded administrator has MustChangePassword = false).

**Fix:** Answer packaging's open question with loopback binding: '127.0.0.1:4200:8080' and '127.0.0.1:5080:8080' in the base file, and the same prefix in each overlay's !override list. The CI check on the published port still holds. In the README, add one sentence on how to expose the dashboard deliberately: change the bind address together with Dashboard__Admin__Password and Dashboard__ApiKey, and put TLS in front.

## 5. [major] (auth-backend, packaging)
Sign-in throttling can be turned against the users, and one of its two layers disappears behind a proxy. (a) Lockout: after five failures the account is refused for 15 minutes even with the right password. Five requests every 15 minutes keep a known username out for good; the demo's is admin, and the only administrator may be the target. (b) The auth limiter is one fixed window of 20 per minute per client address. On Docker Desktop nginx normally sees the bridge gateway as the peer for every browser, and behind an outer load balancer ForwardLimit 1 yields the balancer. All users then share one bucket, and 20 junk requests a minute deny sign-in to everyone. (c) A client that reaches port 5080 from inside the trusted ranges can forge X-Forwarded-For, get a fresh bucket per request and force unbounded password hashing, because unknown usernames are hashed too.

**Evidence:** Blueprint auth-backend section 4, CredentialVerifier steps 2-3 ('Unknown, disabled or LockoutEndUtc > now: ... return null, count nothing'), section 5 services step 8, section 11 (AuthPerMinute 20; lockout 5 attempts, 15 minutes; 0 disables). Blueprint packaging section 5 (ForwardLimit 1, private ranges trusted) and its risk list. The gateway address on Docker Desktop is an expectation to confirm in live verification.

**Fix:** Limiter: key the login and password-change window on client address plus normalised username (hashed), and keep a per-address window only for setup. Add a global concurrency limiter around password verification (for example permits = max(2, cores/2) with a short queue, 429 when full) so hashing cannot starve the API. Lockout: keep it, but let a browser that has signed in before bypass the shared lock with a Data-Protected, HttpOnly 'known device' cookie bound to the user id (the OWASP device-cookie pattern). An outsider can then only lock out unknown browsers. If that is out of scope, record the residual risk in ADR 0006 and document the escape that already exists (restart with Dashboard:Lockout:MaxFailedAttempts=0) in the guide's Troubleshooting section. Log a Warning when forwarded headers arrive from a peer that is not trusted, since the limiter is then keyed on the proxy.

## 6. [major] (auth-frontend, auth-backend)
The SPA and the API disagree on the administration payloads, and the API would silently accept the SPA's version. The SPA sends enabled and teamIds on user create and update. The API's records use IsEnabled, have no enabled flag on create, and treat team membership as writable only through the team. System.Text.Json skips unknown members and the update fields are nullable, so 'disable this user' and 'remove from team' on the user page would return 200 and change nothing.

**Evidence:** Blueprint auth-frontend section 3 (AdminUser.enabled; CreateUser and UpdateUser include enabled and teamIds; Role.builtIn; lastLoginAtUtc) against blueprint auth-backend section 7 (CreateUserRequest; UpdateUserRequest(DisplayName, IsEnabled, Grants); RoleResponse.IsBuiltIn; UserResponse.LastSignInAtUtc; 'Team membership is written only through the team payload'). Other mismatches: setup_closed versus setup_unavailable; a wrong current password as errors.currentPassword versus code invalid_credentials; passwordMinLength absent from SessionResponse; a refused hub subscription throws versus returns false. C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Program.cs:26 configures the JSON options with no unmapped-member handling.

**Fix:** Adopt the API's names in the SPA models and decide once whether a user payload may write teamIds. Make drift fail loudly: set JsonUnmappedMemberHandling.Disallow on the /api/auth and /api/admin request records, so an unknown member is a 400 validation problem. Add one contract test per request type that posts the SPA's fixture JSON to the API, and an API test that a PUT with isEnabled=false ends that user's session.

## 7. [major] (auth-backend (auth-frontend relies on it))
Live connections can outlive the credentials that opened them. A WebSocket is authenticated once, at connect; the per-request security-stamp check never runs for it. The blueprint aborts connections only from AccessAdministrationService. A self-service password change, which rotates the stamp precisely to end other sessions, leaves the user's other sockets open and still receiving SagaUpdated and TimelineEntryAdded. So does sign-out. There is also no absolute session lifetime: a detail page that refetches on every push keeps sliding the cookie indefinitely, and sign-out does not invalidate a copied cookie.

**Evidence:** Blueprint auth-backend section 4 ('rotated on password change, administrator reset, disable and enable'; AccessAdministrationService 'notifies IAccessChangeObserver'), section 7 (POST /api/auth/password: 'cookie reissued'), section 9 (registry and observer; CloseOnAuthenticationExpiration covers ticket expiry only), section 5 (sliding expiry only). C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Hubs/SagaHub.cs:28-41 (membership is decided at subscribe time).

**Fix:** Call the observer for the user on every stamp rotation and on sign-out: POST /api/auth/password, POST /api/auth/logout, administrator reset, disable and delete. Store the sign-in time as a ticket property that survives sliding renewal, and reject the ticket in ValidatePrincipal after Dashboard:Session:AbsoluteTimeoutHours (for example 24). Optionally offer 'sign out everywhere', which rotates the stamp. Tests: after a password change the other session's hub connection is aborted; a ticket past its absolute lifetime gets 401.

## 8. [major] (auth-backend, engine-snapshots, detail-ux)
Redaction without sagas.data covers payloadJson and the state blob only. The errorMessage field is the exception text thrown by saga code, which often carries business values (an order, a customer, a declined card). It reaches view-only callers through /timeline, through /map and through TimelineEntryAdded pushes. The blueprint says the map 'carries no payloads', but each SagaMapEvent copies ErrorMessage. Only custom roles are view-only, and those are exactly the roles someone creates to hide data.

**Evidence:** C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Core/Runtime/SagaOrchestrator.cs:155, 665 and 872 and C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Core/Dsl/CompensationRunner.cs:58 (errorMessage: ex.Message). ## 9. [minor] (auth-backend)
The CSRF and origin checks are keyed on path prefixes, and a query-string API key skips CSRF. The antiforgery check applies 'under /api' and the origin check 'for /hubs only'. Routing is case-insensitive and port 5080 bypasses nginx, so a prefix test written with an ordinal comparison would miss /API/... or /HUBS/saga. An unsafe endpoint later mapped outside /api would skip antiforgery without anyone opting out. Separately, a request authenticated by the API key is exempt even when the key came in the access_token query string, which a cross-site form can supply. Where the key is known (the committed demo value) and its role allows retry, the body-less retry endpoint is reachable by a drive-by request.

**Evidence:** Blueprint auth-backend section 5, pipeline steps 3 and 5. C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Auth/ApiKeyAuthenticationHandler.cs:50-52 (query-string key accepted on every path). C:/Users/rafae/Documents/Projects/vSaga/dotnet/src/VSaga.Dashboard.Api/Endpoints/SagaEndpoints.cs:59 and 128 (retry binds no body).

**Fix:** Decide by endpoint, after routing. Enforce antiforgery for every unsafe method on any matched endpoint unless it carries an explicit exemption marker (only the hub), and apply the origin check to endpoints carrying a hub marker. Exempt API-key requests only when the key arrived in X-Api-Key or Authorization, and accept access_token only on hub endpoints. Treat 'Origin: null' as a mismatch. Extend EndpointProtectionTests: every non-GET endpoint is antiforgery-enforced or is the hub, and upper-case paths behave the same.

## 10. [minor] (auth-backend)
The API key can be given administrative power, and its audit name can be impersonated. Dashboard:ApiKeyRole may name any role, including Administrator or a custom role with access.manage. A static shared secret could then create users and grants with no antiforgery and no named actor. The username rule also allows a user called api-key, whose retries would be recorded exactly like the key's.

**Evidence:** Blueprint auth-backend section 10 (role resolved 'against the built-ins in code, otherwise the store by name'; claims sub=api-key), section 7 (username rule: 3 to 64 of [A-Za-z0-9._@+-]), section 4 (AuditActor is dashboard:<username> or dashboard:api-key).

**Fix:** Never let the API-key principal satisfy access.manage. Strip it from the key's effective access, answer /api/admin/* with 403 as /api/auth/password already does, and log a Warning at start when the configured role contains it. Reserve the username api-key (ignoring case), or write the actor as dashboard:user:<username>. Warn at start when Dashboard:ApiKey is shorter than 24 characters, because key guesses are not rate limited.

## 12. [minor] (auth-backend, packaging)
Cookie security depends on a correctly forwarded scheme and fails quietly when it is missing. With SecurePolicy SameAsRequest, a deployment behind a TLS terminator that sends no X-Forwarded-Proto, or whose address is not in Dashboard:TrustedProxies, issues session cookies without Secure on an HTTPS site. The hub origin guard then compares an https Origin with an http request and rejects every connection, with nothing telling the operator why. The nginx template also forwards whatever X-Forwarded-Proto the client sent.

**Evidence:** Blueprint auth-backend section 5 (SecurePolicy=SameAsRequest for the session and antiforgery cookies; HubOriginGuard compares with scheme://Host). Blueprint packaging section 2 (map $http_x_forwarded_proto with default $http_x_forwarded_proto) and section 5 (trust is off by default).

**Fix:** Add Dashboard:Session:RequireHttps (default false). When true: CookieSecurePolicy.Always, the __Host- cookie name prefix, HSTS, and startup validation that forwarded headers are configured. Have the hub guard log the received Origin and the expected value at Warning when it rejects. In nginx, pass the client's X-Forwarded-Proto only when an environment switch says an outer proxy exists; otherwise send $scheme. State in docs/dashboard.md that TLS is required for anything beyond localhost.

## 13. [minor] (auth-backend)
Known and unknown usernames take measurably different time. Both paths verify a hash, but only a real, unlocked account then writes to SQLite (RecordFailedSignInAsync), and a locked account switches to the dummy path with no write. The response bodies are uniform, so timing is the remaining signal. A retry entry's actor also shows usernames to anyone with sagas.view on that type.

**Evidence:** Blueprint auth-backend section 4, CredentialVerifier steps 2 and 3; section 8, retry row (sourceService: caller.AuditActor).

**Fix:** Pad every failed sign-in to a fixed floor (for example, complete no earlier than 300 ms after the request started, plus a little jitter), or perform an equivalent no-op write on the dummy path. Reject a username over 64 or a password over 128 characters before any lookup or hashing, with the same 401. Accept and document that usernames are visible on retry entries.

## 14. [minor] (auth-backend, packaging)
The SQLite file holds password hashes, security stamps and the unencrypted Data Protection key ring, so reading it is enough to forge a session for any user. The blueprints set no file modes. The 'never blocks start-up' mode also needs a rule for the key ring. If the repository returns an empty list while the store is unavailable, Data Protection creates a new in-memory key, issues cookies that die at restart, and may sign users out when the store returns.

**Evidence:** Blueprint auth-backend section 4 (IdentityStoreXmlRepository), section 6 (not-ready behaviour) and its risk list ('stored unencrypted in the same SQLite file as the password hashes'). Blueprint packaging section 6 (mkdir and chown only).

**Fix:** Create the directory with mode 0700 and the database with 0600 on Linux, and note in the docs that a backup of the volume is a credential backup. Make the XML repository throw when the store is not ready. Have the auth endpoints and the cookie events check readiness before any Data Protection call, so the answer is 503 or 401 and never a new key. Offer a certificate setting (ProtectKeysWithCertificate) as the documented way to encrypt the ring at rest.

## 15. [minor] (auth-backend, guidance-docs)
Nothing records who signed in or who changed access. Retry attribution lands in the saga log, but sign-in success and failure, lockouts, setup, seeding, password resets and every user, team, role and grant change leave no trace. An administrator can reset another user's password, sign in as them and retry under their name, unseen.

**Evidence:** No blueprint defines log events for /api/auth/* or /api/admin/*; blueprint auth-backend section 7 lists the endpoints only. Blueprint guidance-docs section 6 plans the Authentication and Access control sections with no deployment hardening list.

**Fix:** Emit structured ILogger events with stable EventIds from the auth endpoints and AccessAdministrationService: actor, target, action, outcome and client address. Never log passwords or hashes, and log a submitted username only when it passes the username rule. Document the log category so operators can ship it. Add a 'Deploying beyond localhost' checklist to docs/dashboard.md, and the accepted residual risks to ADR 0006.

## 16. [minor] (auth-backend)
Three gaps in the password flows. A wrong currentPassword on POST /api/auth/password is only rate limited, so a hijacked session can keep guessing the password at 20 a minute. Nothing stops a forced change from 'changing' to the same password. A temporary password set by an administrator stays valid forever if the user never signs in.

**Evidence:** Blueprint auth-backend section 7 (password row: 'cookie user, limiter', 400 invalid_credentials; 'Administrator-created users and administrator resets default to mustChangePassword = true'), section 4 (PasswordPolicy checks length and inequality with the username only).

**Fix:** Count a wrong currentPassword against the account's failure counter and end the session at the threshold. Reject a new password equal to the current one. Give must-change passwords an expiry (for example Dashboard:Password:TemporaryValidHours, default 72), after which sign-in fails with the uniform response and an administrator must reset again.

## 17. [minor] (packaging, auth-backend)
Two small gaps at the HTTP edge. No blueprint owns Cache-Control: no-store for /api responses: packaging assigns it to the API, and auth-backend sets it on the session endpoint only. Port 5080 also serves JSON without nosniff. Second, the nginx error log records the full request line, so a machine client's access_token key appears there whenever the upstream fails, although the access log format omits it.

**Evidence:** Blueprint packaging section 2 (rule 9 on the access log format) and its contract that Cache-Control: no-store on /api/ responses is the API's job. Blueprint auth-backend section 7 (no-store on the session row only).

**Fix:** Add one API middleware that sets Cache-Control: no-store and X-Content-Type-Options: nosniff on every /api response, with a test. Document that machine clients send X-Api-Key and not access_token; restricting access_token to hub endpoints (see the CSRF finding) closes the rest.
