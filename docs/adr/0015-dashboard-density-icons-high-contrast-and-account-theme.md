## Context

ADR 0010 shipped the tokens and the light theme and left four things out on purpose. The maintainer has now asked for
them:

1. **One density.** Every page is laid out at one spacing. An operator reading a long saga list or a wide table next to
   a terminal gets few rows per screen; someone on a touch screen or with low vision wants more air, not less.
   ADR 0010 noted that "the spacing tokens make it cheap to add later". They are used by the global classes and by most
   component stylesheets (`src/styles.scss`, `*.scss`), but about fifty values between scale steps are still `rem`
   literals (`DESIGN.md`, "Spacing, shape, elevation"), so a density change moves what is tokenised and leaves those
   alone.
2. **No icons.** The record ruled out an icon *font* (the container's CSP forbids external fonts, `font-src 'self'`,
   and a font is a dependency) and drew state as CSS shapes. A few places still carry meaning in colour and words
   alone: the four banner tones are told apart by their tint, and the user menu's Account, Theme and Sign out are
   words. The sort arrows, the menu arrow and the checkmark are Unicode text glyphs (`▲ ▾ ✓ ›`), which the system font
   may draw in an unpredictable fallback font.
3. **Two themes, neither strong enough for low vision.** The measured text contrast is 4.5:1 or better (AA). Some
   operators need more (AAA, 7:1), stronger borders and a heavier focus ring. `forced-colors` mode covers people whose
   OS substitutes its own palette; it does not cover people who want a high-contrast look without that mode.
4. **The choice is per browser.** The theme lives in `localStorage` (`vsaga.theme`). An operator who signs in from a
   second browser or a new profile gets System again. ADR 0010 recorded this as a limitation and rejected an API and a
   schema change "for a cosmetic setting". The maintainer has now asked for the choice to follow the account.

Constraints that bound the options: the container's Content Security Policy is
`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'`
(`dashboard-web/nginx/default.conf.template`): no inline script, no external fonts, scripts or styles, but `data:`
images are allowed; `docs/frontend.md` and `AGENTS.md` forbid a new dependency or UI library without approval; routes,
authentication and API contracts stay as they are; EF Core migrations are generated by `dotnet ef`, never written.

## Decision

Parts 1 to 3 are SPA-only: CSS, templates, two small services and `public/theme-init.js`. No API, route, dependency or
build change. Part 4 is the one part that is not: it adds a column, an endpoint and a field of the session (see its
section, which records what was built).

### 1. Density: Comfortable (default) and Compact

- A second user-menu group, **Density**, with **Comfortable** and **Compact**, stored in `localStorage` under
  `vsaga.density` (`compact`; absent means Comfortable) and applied as `data-density="compact"` on `<html>` by
  `DensityService`, and before first paint by `theme-init.js` (the same reason, and the same CSP-friendly file, as the
  theme).
- Compact is a re-definition of the spacing tokens under `:root[data-density='compact']` (`--space-2` to `--space-8`
  drop by about a quarter; `--space-1`, 4 px, does not move) plus a tighter body line height (1.5 to 1.4). Nothing else
  is a density rule: a component that uses the tokens follows, one that uses a literal does not. That is a stated limit
  of the switch, not a defect to hide: the work to finish it is the snapping of the fifty literals, which ADR 0010 left
  to the maintainer.
- Compact never takes a pointer target below the 24 px `DESIGN.md` requires: a button's vertical padding is
  `--space-1`, which is why that step is held fixed. The row of the saga list is a whole-row target.
- Density is independent of theme: any theme with either density.

### 2. Icons: SVG drawn by the stylesheet, no font, no request, no dependency

- A small set of masks in one partial (`src/styles/_icons.scss`): an SVG path as a `data:` URL in `mask-image`, painted
  with `background-color: currentColor`, so an icon takes the text colour in every theme and the high-contrast one.
  `img-src 'self' data:` already allows a `data:` image; nothing is fetched. A `-webkit-mask` copy keeps Safari
  releases that predate the unprefixed property working.
- Under `forced-colors: active` a background is replaced by the system, which would paint the icon as `Canvas`; the
  icon sets `forced-color-adjust: none` and `background-color: CanvasText`, so it stays visible.
- An icon is decorative: `aria-hidden`, beside a word, and never the only cue. It adds a second cue to what already
  has a word.
- Where: the four banner tones (information, success, warning, error: a CSS `::before` on `.banner--*`, so the 33 banner
  usages gain it without a template edit); the user menu's Account, Sign out, and each Theme and Density option. Not
  where a CSS shape already carries state (the status dots stay shapes), and not as ornament elsewhere (`frontend.md`:
  "Decorate. No ... icons ... unless they serve a stated purpose").
- The Unicode glyph arrows and the check are left as they are in this change: they work, and replacing them is a visual
  change with its own verification for no stated benefit.

### 3. A high-contrast theme: the fourth choice

- The user menu's Theme group becomes **System / Light / Dark / High contrast**; the stored value is `high-contrast`,
  applied as `data-theme='high-contrast'`. System does not select it by itself: `prefers-contrast: more` is not read (see
  options).
- A black page, white text, text and status colours at 7:1 or better on every surface and on the 12 % tints
  (measured; the numbers are in `DESIGN.md` beside the other two themes), UI boundaries (`--border`, `--border-control`)
  at 6:1 or better and 19.8:1, links always underlined, a 3 px focus ring. It is one palette, dark-based: a light high-contrast
  palette is not built.
- It is a third palette mixin beside the dark and light ones (`src/styles.scss`), so a new token is added in three places
  and the spec that lists the tokens fails if one is missed.

### 4. Account-level choice: built

Parts 1 to 3 were per browser. The maintainer asked for the choice to follow the account; it was accepted as the
design below and built on 2026-11-09. The design, and then what the build settled that the design left open:

- **Storage.** One nullable column on the identity store's `Users` table, `DisplayPreferences` (text, at most 256
  characters), holding a small JSON object, `{"theme":"dark","density":"compact"}`. A column of JSON instead of one
  column per setting so that the next preference is not another migration; the API validates the object against a closed
  set of keys and values (an unknown key is dropped, an unknown value is a 400), so the column never holds free text from
  a client.
- **Migration story.** A new migration from `dotnet ef migrations add AddUserDisplayPreferences --context
  DashboardIdentityDbContext --project dotnet/src/VSaga.Dashboard.Identity.Sqlite --startup-project
  dotnet/src/VSaga.Dashboard.Api --output-dir Migrations` (CONTRIBUTING), adding a nullable column. No backfill: `NULL`
  means "no account choice", and the existing rows keep it. The identity store is applied by migration at startup, so
  an existing volume upgrades in place and a rollback to the previous image ignores the column. The saga stores and the
  persistence conformance suite are not touched: this is the dashboard's own SQLite file, not a saga provider.
- **API.** `GET /api/auth/session` gains `preferences` (null when none, and for the API-key session, which has no
  user); `PUT /api/auth/preferences` (authenticated, antiforgery like the other POSTs) replaces it. The store interface
  `IDashboardIdentityStore` gains one method, `SetDisplayPreferencesAsync(userId, json)`.
- **SPA.** After sign-in the services read `session.preferences` and apply it; a change writes through. `localStorage`
  stays as the cache that `theme-init.js` reads before first paint (the CSP forbids doing it from the session), updated
  on every sign-in, so a different account on the same browser does not flash the previous one's theme for more than the
  first load. The first sign-in of an account with no stored choice uploads the browser's current choice once, so
  nobody loses the choice they already made; after that the account wins.
- **Why it was not in the first change.** It is a schema change (a generated migration, which the maintainer asked to be
  asked about), a store-interface change with its tests in three projects, a session DTO change and a live check on the
  compose stack's identity volume. Half of it (a column nothing reads, or an endpoint with no migration) is worse than
  none, so it waited until all of it could land together.

**What the build settled** (the design above stands; these are the points it left open or that the build changed):

- **A request that names an unknown key is a 400, as every other request body under `/api/auth` is.** The design said
  an unknown key "is dropped". On the way in the API is strict (an unknown or duplicate member, a value outside the
  closed set, a non-object body: `400` `validation` naming the member), because silently ignoring a member is what the
  rest of the API refuses to do. The tolerant side is the read: `DisplayPreferences.Parse` drops an unknown key and an
  unknown value from the stored text (written by a newer image, then rolled back) instead of failing a sign-in.
- **`system` and `comfortable` are values, not absences.** A null member means "no account choice for it", so the
  browser's own stays; `{}` clears the account's choice. The account can therefore say "follow the OS" and have it win
  over a browser that had picked Dark.
- **No second read method.** The design named one new store method, `SetDisplayPreferencesAsync(userId, json)`, and that
  is the only one. Reading rides on what is already read: `DashboardUser.DisplayPreferences` carries the stored text, and
  `CallerAccessResolver`, which loads the user on every request, parses it into `CallerAccess.Preferences`, so the session
  needs no extra query. `UpdateUserAsync` leaves the column alone, so an administrator's edit of a user never undoes a
  preference, and writing it touches nothing else (not `UpdatedAtUtc`, not the security stamp).
- **`PUT` answers `200` with what is now stored**, not the whole session: nothing about the identity changed, so the
  antiforgery token and the cookie stand.
- **The upload of the browser's choice is conditional.** An account with none is given the browser's choice only when
  it is not System and Comfortable: with nothing to lose there is nothing to upload, and the account stays "no choice".
- **A failed write is retried while the page lives, and not overwritten meanwhile.** The SPA keeps a choice that could not
  be saved as unsaved and sends it again at the next session read, instead of letting the account's older value replace
  what the user just picked. The flag is in memory: a reload before the retry lets the account's stored choice win (a
  stated limitation; persisting the flag in `localStorage` would close it). A session read that was sent before a
  confirmed change cannot undo it (`preferencesEpoch` in `AuthService`).
- **Switching account on one browser** applies the new account's choice. An account with none that signs in on a
  browser still holding the previous account's non-default choice is given that choice, which is what "the browser's
  current choice" means; signing out does not clear the cache.

## Options weighed

- **Density by a scale factor on the root font size.** One line, but `rem` is also the type scale, so it scales text and
  the 24 px targets with it. Rejected: density is about space, not size.
- **Density by redefining the spacing tokens (chosen).** Uses what ADR 0010 built for it. Limited to what is tokenised.
- **Three densities.** More to verify and nobody asked; two cover "more rows" and "more air".
- **An icon font or an icon package (Lucide, Material Symbols, Font Awesome).** A dependency or a font file; the CSP
  forbids external fonts and `AGENTS.md` forbids a dependency without approval. Rejected, as in ADR 0010.
- **An `<app-icon>` component with inline `<svg>` in templates.** Works everywhere (and keeps `currentColor` in
  forced-colours mode without a rule), but the banners alone need 33 template edits and a TypeScript map of paths for a
  decorative mark. A CSS mask gives the same pixels from one partial. If a later icon needs interaction or animation, the
  component is the right tool then.
- **CSS shapes only (no SVG).** Right for a dot or a chevron; a sun, a moon or a person cannot be drawn well with borders
  and `clip-path`.
- **A sprite file (`icons.svg`) referenced with `<use>`.** One more request, and `<use>` across files is fiddly under a
  strict CSP. Rejected.
- **High contrast from `prefers-contrast: more` only.** Would help people who already set it at no cost to anyone, but it
  would override the Light or Dark palette an OS user also chose, and there is no light high-contrast palette to give a
  light-mode user. Deferred; a menu choice is explicit and testable, and the media query can select the same palette later.
- **A light high-contrast palette too.** Doubles the palette to measure and keep true. Deferred until someone asks.
- **Per-account storage as a separate `UserPreferences` table, key and value rows.** Flexible, but a join and a second
  table for two values. A JSON column on `Users` is the smaller thing that works.
- **Per-account storage in the session cookie or in a claim.** Would need no migration, but the cookie is rewritten only
  at sign-in, so a change would not follow the user until the next sign-in, and the cookie is size-limited. Rejected.
- **Keep it per browser (ADR 0010's answer).** Free, and already built. Rejected by the maintainer's request; it is now
  only the behaviour for a visitor who is not signed in, and the cache `theme-init.js` reads.

## Consequences

- **Easier.** An operator can get more rows per screen or more air; a low-vision user can pick a high-contrast look
  without an OS setting; banners and the menu have a second, non-colour cue; the next icon is one entry in a partial.
- **Harder.** Three palettes to keep true (every colour token in three places, measured three times); two stored
  settings and a second service to keep in step with `theme-init.js`, which a spec pins; every new spacing literal that is
  not a token is now also a density bug.
- **Stated limitations.** Compact moves only what uses the spacing tokens; about fifty literals stay put. The
  high-contrast palette is dark-based only and is not selected by `prefers-contrast`. The choices follow the account, but
  the first paint can only use the browser's cache (the CSP forbids reading the session from an inline script): a
  browser that blocks storage, or a first visit on a new browser, shows the default look until the session is read, and
  the sign-in page uses the browser's choice. A change made in another browser arrives at the next session read (sign-in,
  or returning to the tab), not live. The account holds two choices, not a general settings store.
- **A dependency on the CSP.** The masks need `img-src ... data:`; if a later hardening removes `data:`, the icons
  vanish silently (the words stay, so nothing is lost but the second cue). `DESIGN.md` records the dependency and the
  stack check watches the console.
- **Browser support.** `mask-image` is unprefixed from Chrome 120, Firefox 53 and Safari 15.4; the `-webkit-` copy covers
  the older ones. Firefox and Safari had never been looked at (ADR 0010, "Never tested"); this change was checked in the
  compose stack in Playwright's Chromium, Firefox and WebKit builds (WebKit on Windows, which is not Safari itself): the
  menu, every theme and both densities, reload persistence and no horizontal overflow at 360 px. Not run: real Safari, a
  real Windows High Contrast session (only the browsers' `forced-colors` media emulation), a screen reader.
- **Part 4, what was checked.** Unit and API tests (the store contract, the resolver, 20 endpoint cases, the SPA's
  session, the preferences service and the menu), then the compose stack (Wolverine overlay, Chromium, the console
  watched): signing in, choosing Dark and Compact in the menu (two `PUT 200`, the server holds them); a second browser
  context with empty storage signing in as the same account and coming up Dark and Compact with the right items
  checked and no upload; a change in that context reaching the first at the next session read; a `PUT` that fails
  (kept on the page, not reverted by a session read, re-sent once the network is back); an account cleared server-side
  receiving the browser's choice exactly once on reload; `400` for a value outside the set and for an unknown member,
  `400 antiforgery` without the token, `401` anonymous, `403` for the API key (whose session has `preferences: null`).
  The migration was run on an old-schema identity file (made by the previous image on a fresh volume): the new image
  upgraded it in place, the existing user and password survived, and the previous image then ran against the upgraded
  file and signed in and listed users, so the rollback claim holds for that image. Not run: Firefox and WebKit for this
  part (the earlier parts were), a real Safari, an identity file with many users, and a storage-blocked browser.
- **Part 4 cost one generated migration** (`AddUserDisplayPreferences`, a nullable column, no backfill) and has a rollback
  story: a nullable column an older image should ignore.
